# 历史记录云同步客户端改进设计

状态：建议方案，未实现。

## 1. 目标与约束

用户提供的复现场景：两台设备登录同一账户；A 抽人后在设置页手动同步并显示完成；B 随后手动同步也显示完成，但历史页面没有刚生成的记录。现有日志只易于看到 KV 写入和 `Pushed students`，无法判断拉取过程。

目标是使“同步完成”表示本轮上传、拉取、本地持久化和页面数据发布都完成，并让记录未出现时能够定位断点。继续使用现有 SECTL KV API、现有 Flutter/Provider 技术栈及本地文件/Web 存储，不要求增加数据库、推送服务、事务或 CAS 服务端接口。

保留云端键和已有记录 UID：

| 内容 | 现有键 |
| --- | --- |
| 点名/抽奖历史分片 | `srlite.history.v2.<kind>.<deviceId>.<index>` |
| 流摘要 | `srlite.history.v2.<kind>.<deviceId>.meta` |
| 设备注册表 | `srlite.sync.v2.registry` |
| 设备统计贡献 | `srlite.stats.v2.<kind>.<deviceId>` |
| 学生名单 | `srlite.students` |

本次不改变清空历史的产品语义：`clearedAt` 仍表示本机过滤，暂不引入跨设备删除。保留学生名单现有合并规则，但与历史同步分别记录结果，避免每次历史轮询都读写名单。旧 `secrandom.*` 命名空间迁移不属于本次默认范围；运行时应记录协议版本以判断两端是否使用相同版本。

下文中的时延、调度参数及模块拆分均为设计建议，并非用户已指定的需求。

## 2. 已确认的问题与证据边界

本次阅读了记录生成、outbox、KV API、历史流、登录同步、手动同步与历史页面。用 `/tmp/opencode/history_sync_diagnostic_test.dart` 中的模拟 KV 及深拷贝本地存储运行了六个诊断用例，其中一个为正常对照、五个重现缺陷。这些用例断言的是现有缺陷行为，不能当作修复验收通过。

| 问题 | 代码位置 | 确认结果 |
| --- | --- | --- |
| 拉取失败会被上传成功掩盖 | `AppProvider.syncNow` 返回 `pulled || pushed`；`pushAll` 重置全局错误与状态 | 拉取注入 503 后，最终仍返回 true、状态 success、错误 null，并出现 Pushed students |
| 注册表漏项会被发现缓存放大 | `_updateRegistryEntry` 共享读改写；`_discoverRemoteDevices` 缓存 10 分钟；普通手动拉取不强制刷新 | 预热发现缓存后，模拟注册表丢失 A 条目，即使 A 分片存在，B 仍成功返回 0 条；测试验证的是漏项后的结果，未模拟整个并发注册表写入过程 |
| 缺失的中间分片被跳过 | `_readShard` 将 not_found 当空；`readFrom` 继续推进后续分片 | 分片 0 缺失而分片 1 存在，游标跳到 1；分片 0 恢复后也不再被读取 |
| 上传中新增队列记录丢失 | `flushOutbox` 持有旧 outbox 快照，网络完成后清空并整体保存 | 上传暂停期间成功 enqueue 第二条，随后旧快照覆盖队列，第二条既未上传也不再待传 |
| 元数据提交失败的重试不完整 | `appendOwn` 先写分片、最后写 meta；重试 UID 去重后可直接返回旧 meta | 已有一条历史时，再追加一条并让 meta 写入失败，重试清空 outbox 后 meta.total=1 而分片已有 2 条 |
| 正常对照 | 两个不同 deviceId、注册表与 KV 正常、顺序执行 | A 推送后，B 可以拉到一条新点名历史 |

另外可由代码确定的薄弱点：

- KV GET 与拉取服务没有成功过程日志；“只看到上传”不代表未执行 GET。
- 登录、自动推送、重试、手动同步、回前台同步没有统一的运行队列；页面自己的 busy 状态只保护该页面按钮。
- 历史逐条执行文件读改写；本地生成和远程合并可相互覆盖。现有诊断没有动态复现这一条，应补并发回归测试。
- 点名页面消费 Provider 内存历史；抽奖历史及其详情页各自缓存文件结果，文件变化不保证现有页面更新。这不能单独解释用户所说的点名场景。
- 历史页的班级选项只来自现有学生名单；有记录但已无对应名单的班级可能无法选择，需把历史中的班级纳入选项。
- 新记录可能退回 `unknown` 设备前缀；AppProvider 与服务独立解析设备身份。两台实际设备是否出现身份或协议不一致，仍需运行日志证明。

尚未取得用户两台设备的分阶段日志、KV 内容和运行版本，所以不能声称已经确定真实故障唯一原因，也不能据此推断服务端是否强一致、是否存在缓存或索引延迟。

## 3. 方案选择

推荐保留 v2 每设备历史流，在客户端补齐可靠同步引擎。现有“每设备单写者、UID 并集、本地 outbox”的方向可以保留。

只增加日志、修改完成条件可以先定位问题，但不能修复队列丢失和游标漏读。将历史改成全量文件上传会增加传输和覆盖竞态；改成每条记录一个新 KV 或全新协议需要迁移和更多键，目前没有必要作为第一步。

## 4. 客户端职责

建议职责划分如下，文件名可由实现者按现有风格微调：

- `SyncCoordinator`：所有同步入口的排队、合并请求、阶段结果和重试。
- `HistoryRepository`：点名和抽奖的本地记录写入、按 UID 批量合并、持久化完成后的通知。
- `CloudSyncService`：云端设备发现、各数据类别的传输；不再单独决定整轮“同步完成”。
- `HistoryStreamManager`：分片提交计划、提交恢复、快照读取与完整性校验。
- `SyncLocalStore`：本地状态、outbox 与提交计划的串行修改及故障恢复。
- `AppProvider`：向界面提供同步报告和两种历史的已提交视图。

数据路径为：业务写入 → 本地持久化意图 → 本地历史/统计落盘 → 发布本地视图并调度同步 → 历史分片/meta 提交 → 按批次确认 outbox；拉取路径为：设备发现 → 读取指定 meta 快照内的增量 → 校验 → 按 UID 批量落盘 → 提交游标 → 发布视图。

## 5. 一轮手动同步的准确含义

### 5.1 排队和时序

`AppProvider` 构造时暴露 `ready` Future；登录同步必须等本地加载及恢复结束。所有网络同步入口都进入同一个协调器，手动操作和自动操作共用一条执行队列。

手动同步的默认顺序保留“拉取后上传”，以延续现有名单云端优先行为：

1. 等待点击前已经开始的本地记录保存及恢复任务完成，捕获本轮 localRevision。
2. 强制刷新设备发现，读取远端历史并合并落盘。
3. 更新历史游标及页面视图；统计与名单分别处理，不阻断已经验证完整的历史落盘。
4. 上传本轮捕获的待传历史批次，确认相应 meta 已提交，再确认 outbox；处理应上传的统计与名单。
5. 汇总各阶段报告；点击之后新产生的记录保持待传，由下一轮处理。

后台任务运行时点击手动同步，不返回“忙/跳过/成功”。协调器登记一个带强制发现要求的后续轮次；手动 Future 在满足该请求的轮次结束后返回，不能只等待点击前已经开始且读过旧云端状态的任务。

上传和拉取都尽量执行，独立阶段失败时不覆盖其他阶段的错误。网络请求设明确超时；超时与失败保持待处理任务。若存在结果不确定的写请求，禁止在原流上启动另一份追加计划，按第 8 节的冻结流规则恢复；一次读回成功不能证明更早的写请求已经停止。

### 5.2 结构化结果

用 `SyncReport` 替代单一 bool。至少包含：

```text
runId, trigger, startedAt, finishedAt, localRevision
discovery: complete | degraded | failed, knownDevices, discoveredDevices
historyPull: success | failed, fetched, inserted, duplicates, filtered
historyPush: success | failed, acknowledged, pendingAfter
localApply: success | failed, revision
stats: success | failed | unchanged
students: success | failed | unchanged
errors: [{phase, kind?, stream?, key?, reason, retryable}]
overall: complete | partial | failed | skipped
```

`complete` 要求本轮计划内的发现、历史拉取、上传、落盘、游标提交、视图发布及其他应处理类别均成功或可验证为无变化。本轮后新增的记录仍可待传，须明确展示队列数。拉取 0 条且检查过程完整是有效结果；不能要求每轮都有新记录。

示例文案：“同步完成：下载点名 1 条、上传 0 条”；“上传成功，历史拉取失败，将自动重试”；“已检查 2 台设备，无新历史”。发现降级、流不完整、自动开关关闭而跳过操作，均不能显示无条件完成。

“完整”只针对本轮可枚举并成功读取的云端视图，不能声称此刻所有设备都已同步。KV 一致性及分页快照能力未知；若服务端存在可见性延迟，日志和后续退避轮次需保留这一事实。

## 6. 设备发现

手动同步和历史页手动刷新强制执行 `listKv` 全部分页，绕过当前 10 分钟缓存。候选设备取注册表、键列表和本地已知设备集合的并集。已发现设备持久化，不因单次注册表漏项而移除。

发现失败时仍可读取已知流，但本轮标记 degraded/partial 并说明发现未完成。注册表保留为提示性索引，不能作为完整性依据；不以现有 `patchKvField` 推断服务端具备原子合并能力。

普通轮询可复用短期设备缓存；手动操作始终强制发现。当前 `listKv` 返回 value 而非仅键，数据量大时会增加传输；实现应统计分页、字节数和耗时，避免在一次同步中重复执行三次设备发现及注册表拉取。现有 API 未暴露前缀过滤，不把它当作可用能力。

所有新记录与上传使用同一个已初始化的设备 ID，禁止 `unknown`。现有 UID 不重写。发布版本和 deviceId 的短哈希进入日志；若两个实例共享同一个写者身份，必须解决单写者互斥，不能依赖 KV 覆盖来仲裁。桌面同数据目录使用进程锁、Web 同源使用跨页写者锁；不具备锁能力时为独立运行实例分配独立写者身份。不同设备复制本地数据的身份恢复规则在实现中需保守处理，避免把两个设备当作一个写者。

## 7. 本地持久化与 outbox

### 7.1 先解决丢队列

outbox 的 enqueue、claim、ack、clear 必须经同一个短时存储锁执行。上传时仅认领一份不可变批次并释放锁，再进行网络访问。成功后重新读取最新队列，仅删除本批次已确认的 UID；禁止清空旧对象后覆盖全部队列。

同一 kind/device 只能有一个上传计划在执行。上传期间新入队的记录留给下一批，不等待网络锁。点名及抽奖的保存钩子统一返回 Future，记录保存与入队完成后才认为业务写入已提交；取消抽奖侧 fire-and-forget 入队。

### 7.2 异常恢复

仅串行调用三个文件写入不是事务。长期实现建议扩展现有本地 outbox 格式，使其同时承担写入意图日志（WAL）；云端 schema 不变。意图至少包含 opId、kind、UID、完整记录、localRevision、预期统计/序号状态以及 localApplied/cloudCommitted 标记。

保存意图后，按 UID upsert 本地历史，应用该 revision 对应的统计/序号目标状态，再标记 localApplied。恢复时先按 revision 顺序重放，完成后才接收新业务操作；统计恢复写入目标快照或等价的幂等状态，不能重复 increment。上传只认领 localApplied 的记录。只有本地已应用且云端已确认的意图才能清理。

本地文件应使用带版本/校验的临时文件和替换写入，并保留可恢复的上一版本；Web 原子替换一个已序列化的日志值并将配额等失败向上传递。不能将解析错误、I/O 错误或存储配额错误当作“空历史/空队列”并继续成功。文件替换、flush 与锁的具体平台实现由实现者选择，须通过故障注入验证。

现有无状态 outbox 数组可兼容读取，迁移成 localApplied 的待传意图；首次升级还应核对本地历史与云端并集，修复此前“本地已保存但从未成功入队”的记录。清空操作也通过本地锁/日志更新其筛选和队列状态，避免与入队交错；不扩展成云端全局删除。

## 8. 云端分片提交与恢复

保留现有 100 条/48 KiB 分片策略，但不再每次追加都读取全部本机历史 UID。首次建立本机流基线及完整性校验后，维护持久化的已确认 UID 索引，正常追加只需要尾片、必要的新片及 meta。

每批追加在联网前持久化不可变的 append intent，包含已读取的 base meta、各目标分片完整内容/校验值、目标 meta 与本批 UID。顺序为：写分片 → 写目标 meta → 必要时读回验证 → 本地标记云端提交成功 → 确认该批 outbox。

写入失败或响应丢失时，恢复同一份计划，重复写相同分片和相同 meta；不得因在分片里看到了重复 UID 而跳过 meta 提交。未恢复的计划完成前不追加下一批。注册表更新是索引维护，失败须记录并修复，但记录提交以分片和对应 meta 的完成状态为准。

### 8.1 超时后迟到写入的边界

现有 API 没有请求版本前置条件或幂等键。不能假定客户端 Future 超时会取消服务端写入，也不能仅凭重试成功或一次读回就排除更早的同键写入将来才完成。如果基于未经证实的保证继续修改同一尾片，旧请求可能覆盖后续批次。

建议默认采用保守策略：一次写入出现传输结果不确定时，将该历史流持久化标记为 frozen，并只允许重放当时那份不可变 append intent；该流以后不再接受新批次。旧批次确认成功后，新批次使用新随机 writerId 开始另一条流。所有晚到和重试的写入只涉及冻结流中相同的目标值，不会覆盖之后的新流。

writerId 使用现有历史键中的 deviceId 槽位，键形状和记录 UID 不变；设备安装身份 installationId 与写者流身份 writerId 分开。记录 UID、序号和统计贡献仍属于 installationId，不能因为流轮换把统计作为另一台设备重新求和。meta 可增加旧客户端会忽略的 installationId 字段用于显示归属；接收方对各 writerId 独立维护游标、按记录 UID 去重，设备数与流数分别统计。新客户端仍读取旧流，旧客户端仍可通过现有键扫描发现新 writerId。

该策略还依赖单键成功写入具有完整替换语义，不要求跨键事务或服务端请求可取消。若后续确认服务端能够提供更强的写入有序性，再评估减少冻结流；确认之前不得以可变尾片的读回作为迟到写入安全证明。是否存在列举/读取可见性延迟仍应独立记录，失败或不完整的读取不推进游标。

处理已经存在的损坏流时，只有该流写者可以根据 KV 枚举出的分片重建自身 meta；先验证连续性、记录可解析性与 UID。无法确定连续完整性时保留 outbox 并报告错误，不能删除旧数据或猜测 total。接收端发现其他设备流损坏只报告和保留游标，不替对方覆盖 meta。

KV 没有提供跨键事务，因此接收方必须按已读取的 meta 快照解释分片：尾片读取至该快照的 `last_shard_count`，不能提前消费尚未发布 meta 的追加内容。

## 9. 拉取完整性、游标和历史展示

分片读取结果应区分“不存在”“空片”“解析失败”“网络失败”。在 meta 已声明存在的范围内，missing/格式不合法/尾片长度不足都属于流不完整；停止该流，不能越过缺片提交后面的游标。其他独立设备流可以继续，但整轮报告为 partial。

为本地游标增加 consumedTotal，保留现有 shard/count 便于兼容。按 meta 固定快照检查本轮读取数量与 `meta.total - consumedTotal` 是否一致；尾片长度按该 meta 截断。游标越界、total 回退或其他不一致触发重新核对，不能直接返回空并标成功。

本地写入使用按 UID 批量 upsert，在短时锁内与本机新增记录合并后落盘；成功落盘后才更新游标，最后向 Provider 发布视图。中途崩溃可重读并去重，不能出现“游标已提交、记录未落盘”。一批中故障时，已落盘 UID 可保留，但该流游标不得越过未验证/未提交的范围。

升级时执行一次完整核对：旧游标没有 consumedTotal，且可能已经跳过缺片，不能直接信任；对发现的各设备流从头按 UID 并集合并，包括本机自己的云端流，并保留本机 clearedAt 过滤。核对验证成功后建立新游标。常规拉取使用增量，不每次登录清空游标或获取全账号完整快照。

点名历史、抽奖历史及详情页统一订阅 Repository/Provider 的已提交数据。同步结束后无需额外点击刷新才能看到新增数据。班级/奖池选择器合并“现有配置”和“历史记录”中的选项，当前筛选不包含新增记录时提供可理解的提示。按抽取时间倒序、UID 作稳定次序，避免用不同设备的本地递增 id 进行全局排序。

## 10. 日志与状态展示

信息级日志记录每次手动/自动轮次的摘要；调试级记录分片细节。失败不被下一阶段成功清空。日志内容不包含 token、学生姓名或完整记录；UID 和 deviceId 使用稳定短哈希，保留跨阶段关联能力。

建议字段：runId、trigger、协议/应用版本、设备短标识、stage、耗时、HTTP 状态及业务错误、设备发现来源、kind、cursorBefore/After、meta.total、读取/新增/去重/过滤数量、本地 revision、待传数量。过滤必须有理由，区分 duplicate、clearedAt、sameWriter、invalidRecord 等。

期望能看到类似摘要（示例为格式建议）：

```text
sync.start run=R12 trigger=manual localPending=1 localRevision=42
sync.discover run=R12 source=registry+kv forced=true devices=2 pages=1 complete=true
sync.pull run=R12 kind=rollcall stream=A cursor=0:8 total=9 fetched=1
sync.apply run=R12 kind=rollcall inserted=1 duplicate=0 filtered=0 revision=43
sync.cursor run=R12 stream=A kind=rollcall committed=0:9 consumedTotal=9
sync.push run=R12 kind=rollcall batch=B7 acknowledged=1 pendingAfter=0
sync.end run=R12 outcome=complete downloaded=1 uploaded=1 elapsedMs=430
```

若失败，最后一行明确 `outcome=partial phase=historyPull reason=missingShard`，而不是只出现后续 Pushed students。日志中的 skip 与 failed 必须可区分。

## 11. 自动同步时效

在手动同步可靠性完成后，建议以下默认策略：

| 触发 | 行为 |
| --- | --- |
| 本地历史提交 | 300–800 ms 合并相邻写入，首条待传不晚于 2 秒尝试上传；持续抽取也有最大等待上限 |
| 手动同步/下拉刷新 | 排队执行，强制设备发现，不受自动同步开关限制；仍要求登录 |
| 登录/恢复会话 | 等 ready 和恢复完成后执行增量同步，首次/异常时核对 |
| 回前台/打开历史页 | 立即或 2 秒短节流拉取，避免当前 5 分钟门槛 |
| 前台历史页可见 | 约 15 秒轮询历史摘要/增量 |
| 其他前台页面 | 约 60 秒轮询历史；统计和名单仅按需要处理 |
| 网络请求恢复成功/在线事件 | 唤醒待处理任务；在线事件仅作提示，HTTP 结果才决定成功 |
| 后台/页面隐藏 | 暂停周期轮询；尽力处理已提交批次，恢复前台补传 |

失败使用有抖动的指数退避；网络/5xx 与鉴权/配额等错误分别处理。达到短期重试上限后仍保留待处理状态，并在前台、手动请求等下次触发重试。周期定时器和重试在登出、自动同步关闭和 dispose 时停止。账户切换使旧轮次失效，防止旧回调写入新账户上下文。

### 11.1 账户归属的建议默认值

本次主要验收是同一账户两端同步。为避免后续实现把共用的本地数据误传到另一个账户，建议本地 workspace 按稳定账户 subject 标识绑定，隔离范围包含历史、统计、clearedAt、序号、outbox、提交意图和发现/游标缓存，不能只隔离同步元数据。退出登录保留该 workspace；属于该 workspace 的离线记录继续归原账户，下一次登录其他账户时不自动并入。

全新未绑定设备的记录归 guest workspace；跨账户/guest 数据转移通过用户主动发起的既有导出导入途径处理，不作为登录的隐含行为。旧版共享目录若有可恢复的账户信息，则首次升级绑定至该账户；无法确定归属时保留为未绑定本地数据，先拉取新登录账户独立基线，不自动上传这批旧记录。这是保守的设计建议，用户未指定账户切换产品规则；不需要为本次同账户问题增加新的确认弹窗。

正常网络和同一 KV 可见性下，目标为：手动同步完成后立即在已提交视图可见；自动上传启动不晚于上述 2 秒上限，历史页通常在一个轮询周期及网络/本地处理耗时内出现。移动端后台和 Web 隐藏标签页的时延不作承诺。

## 12. 分阶段落地与验收

优先级 P0：修复“显示完成但不知是否拉取”的可观测性和确定性缺陷。

1. 增加分阶段报告/日志与手动同步完成规则，错误不被推送阶段抹去。
2. 手动强制发现设备，持久化已知设备并集。
3. 统一所有同步入口的运行队列；outbox 短锁、不可变批次和按 UID ack。
4. 缺片不推进游标，历史按 UID 批量落盘后再提交游标、发布页面数据。
5. 修复失败提交的重试恢复，并执行一次历史完整核对，避免只防新问题却保留旧缺口。

优先级 P1：补齐 WAL、崩溃恢复、身份/多实例互斥与后台重试状态；降低历史上传时延，按页面可见性拉取，减少全量扫描。P0 期间仍明确标注尚未完成跨文件崩溃一致性保证；不能将“正常串行可用”宣传成“崩溃不丢”。

关键验收应包括：

- 用户原路径：A 真实保存一条点名 → A 手动同步 → B 手动同步 → B 本地文件、Provider 和历史页面均包含相同 UID，日志能对应上传及拉取。
- 拉取失败而上传成功显示 partial，保留拉取错误；自动同步关闭时手动按钮仍执行。
- 先缓存设备集合再加入 A/模拟注册表丢项，B 手动操作当轮能重新发现 A。
- 上传期间连续追加记录：已确认批次清理，新记录仍在队列并最终上传；重复/并发触发不丢失也不重复。
- 分片写成功、meta 写失败和响应丢失后重启恢复，meta 与分片一致；不能只验证 UID 没重复。
- 注入旧写请求在重试确认及后续批次之后才完成，验证冻结流不再接收新批次、新流记录不被覆盖，统计贡献不因 writerId 轮换而翻倍。
- 已声明的中间片/尾片短暂缺失时游标不越过，恢复后能取回；旧坏游标通过升级核对找回缺失记录。
- 本机保存与远程批量合并交错，历史文件不互相覆盖；写盘失败不推进游标，Web 配额失败向上传递。
- 清空筛选、历史独有班级/奖池、抽奖已打开页面、同名但不同 UID、同 UID 重放均符合现有语义。
- 网络挂起、登出/账户切换、重启、同本地目录多实例/多标签页均有明确且经过测试的行为。
- 账户 A 的本地/离线记录不因登录账户 B 自动上传；旧版无归属数据保留并可通过既有导入导出取用。

模拟用例必须使用序列化深拷贝的本地存储，不能像当前部分测试那样返回同一可变 outbox 对象，否则会掩盖真实文件存储中的覆盖竞态。首次回归应补一条贯穿业务生成、KV、另一设备 Repository、Provider 和页面的集成测试；仅验证服务返回 newRecords 不足以证明用户可见。

本文件为设计建议。本次未修改产品实现、未连接真实账户云数据，后续应以两端运行日志和上述验收进一步确认实际故障路径。
